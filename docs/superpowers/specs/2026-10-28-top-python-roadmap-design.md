# top-python 개선 로드맵 설계 문서

날짜: 2026-10-28
대체 문서: `TODO.md` (코드 리뷰 메모, 본 문서 승인 후 삭제)

## 1. 의도와 배경

`system_monitor.py`는 단일 파일(~470줄)로 작성된 `top`/`htop` 스타일 터미널 모니터다. 초기 코드 리뷰에서 나온 개선점들이 `TODO.md`에 한글 메모 형태의 비정형 백로그로 쌓여 있었다. 이 문서는 그 백로그를 실행 가능한 단계별 로드맵으로 재구성해, 향후 작업(계획 수립·구현)이 이 문서 하나만 보고 진행될 수 있도록 하는 것이 목적이다.

## 2. 목표 (Goals)

- `top` 실제 동작과 다른 부정확한 부분(우선순위 값, 가동시간 복수형, 가상 로드 평균, `cpu_percent` 호출 위치)을 고친다.
- 단일 파일 구조를 유지보수하기 쉬운 패키지 구조로 재구성한다.
- 핵심 순수 함수에 대한 `pytest` 기반 단위 테스트를 추가해 회귀를 방지한다.
- README에 이미 언급되었지만 구현되지 않은 기능(갱신 주기 조작)과, 사용성을 높이는 기능(cmdline 토글, 코어별 CPU 표시, CLI 인자)을 추가한다.
- 패키징 메타데이터(`pyproject.toml`)와 버전 정보를 갖춘다.

## 3. 비목표 (Non-goals)

- **프로세스 필터링/검색(`/` 키)** — 효용은 크지만 raw-모드 안에서 텍스트 입력 모드를 새로 설계해야 해 구현 비용이 가장 크다. 별도의 설계 문서/스펙으로 분리해 추후 다룬다. 본 로드맵의 패키지 구조(특히 키 입력 처리 모듈)는 이 기능을 나중에 얹기 쉽게 설계하되, 본 작업 범위에는 포함하지 않는다.
- **psutil 모킹 테스트**(`_collect_process_rows`, `_memory_snapshot`, `_cpu_breakdown`을 외부 시스템 없이 검증) — 패키지 구조가 확정되기 전에 작성하면 리팩터링 후 다시 손봐야 할 가능성이 높고, 순수 함수 테스트 대비 가치가 낮다고 판단해 백로그에서 제외한다. 필요해지면 별도 요청으로 다룬다.

## 4. 안티골 (Anti-goals)

작업이 기술적으로는 완료되어도 다음에 해당하면 실패로 간주한다.

- Windows 호환성(ANSI 활성화, `msvcrt` 입력 분기)을 깨뜨리는 것.
- `psutil` 외의 새로운 필수 의존성을 추가하는 것(테스트 전용 의존성인 `pytest`는 예외).
- 색상 비활성화(`enable_color = False`, 파이프/리다이렉트 상황) 시 출력이 깨지는 것.
- 과도한 추상화로 소규모 CLI 도구에 어울리지 않는 복잡도를 추가하는 것(예: 플러그인 시스템, 설정 파일 포맷 등 — 요청받지 않음).

## 5. 제약 조건

- 실행 방법은 계속 간단해야 한다(`python system_monitor.py` 또는 동등한 엔트리포인트).
- 저장소에는 CI가 없다 — 테스트는 로컬에서 수동으로 `pytest` 실행으로 검증한다.
- 문서(README, 커밋 메시지, 본 설계 문서 포함)는 한글을 유지한다.
- `.github/copilot-instructions.md`에 따라 향후 세션 응답은 한국어로 작성한다.

## 6. 검토한 접근 방식 (Approaches)

**구조 변경 범위**에 대해 두 가지 방식을 검토했다:

| 접근 | 설명 | 트레이드오프 |
|------|------|------------|
| A. 단일 파일 유지 | `system_monitor.py` 안에서만 함수/클래스 분리 리팩터링 | 변경 범위가 작고 되돌리기 쉽지만, "색상 상수를 별도 모듈로 분리" 같은 항목을 어정쩡하게 처리하게 됨 (파일 안에 또 다른 네임스페이스를 만드는 식). 장기적으로 `_build_screen` 분리, dataclass 도입 등과 맞지 않음. |
| B. 패키지 구조로 전환 (**채택**) | `top_python/` 패키지 아래 `colors.py`, `models.py`(ProcCacheEntry, Row), `collectors.py`(CPU/메모리/프로세스 수집), `render.py`(`_build_screen` 분리본), `cli.py`(인자 파싱, entry point) 등으로 분리 | 코드 품질 항목들이 자연스럽게 각자의 자리를 찾는다. 테스트도 모듈 단위로 모킹하기 쉬워진다. 대신 import 경로가 늘고, 패키징(`pyproject.toml`)이 사실상 필수가 된다. |

사용자가 B안(패키지 구조)을 선택했다. 패키지/모듈의 정확한 이름과 경계는 "builder가 정할 부분"(7절)으로 남긴다.

**단계 순서**도 검토했다: "버그 수정 → 테스트 → 리팩터링 → 기능 → 폴리시" 순서도 고려했으나, 구조가 바뀌기 전에 작성한 테스트는 리팩터링 중 깨지기 쉬워 다시 손봐야 한다는 단점이 있다. 그래서 "버그 수정 → 패키지 구조 전환 → 테스트 → 기능 → 폴리시" 순서(아래 8절)를 사용자가 승인했다.

## 7. 사용자가 결정한 사항

- **범위**: TODO.md의 미완료 18개 항목 중 16개를 이 로드맵에 포함한다. 분류:
  - 포함(필수) 16개 — 아래 8절 단계표 참고.
  - 별도 스펙으로 분리 1개 — 프로세스 필터링/검색.
  - 완전히 제외 1개 — psutil 모킹 테스트.
- **구조**: 단일 파일이 아닌 패키지 구조로 전환해도 된다 (위 6절 B안).
- **단계 순서**: 버그 수정 → 패키지 구조 전환 → 테스트 → 기능 추가 → 폴리시.

## 8. 로드맵 (단계별)

### Phase 1 — 버그 / 정확도 수정 (패키지 전환 전, 현재 `system_monitor.py`에 바로 적용)

1. `pr`(우선순위) 값을 `"20"`/`"rt"` 고정 대신 `str(20 + nice_value)`로 계산한다(단, `nice_value < 0`인 경우의 표시 방식은 builder가 실제 `top` 동작을 참고해 정한다).
2. `_format_uptime`에서 `days > 1`일 때 `"days"`로 복수형 처리한다.
3. `_loadavg`의 유사(pseudo) 로드값을 매 틱 동일 값 반복 대신 지수 이동 평균(EMA)으로 계산하도록 개선한다.
4. `_collect_process_rows`에서 `proc.cpu_percent(interval=None)` 호출을 `oneshot()` 블록 바깥으로 이동한다.

### Phase 2 — 패키지 구조 전환

5. `system_monitor.py`의 책임을 패키지(예: `top_python/`)로 분리한다:
   - ANSI 색상 상수를 별도 모듈(enum 또는 상수 모듈)로 분리.
   - 프로세스 행을 `dict` 대신 `dataclass`/`TypedDict`로 교체.
   - `_build_screen`을 헤더/CPU행/메모리행/프로세스 테이블 렌더링 등 별도 메서드(혹은 함수)로 분리.
   - `_color`의 `bold + color` 조합 순서를 공통 헬퍼로 통일.
   - 매직 넘버(`80`, `40`, `18`, `11`, `2.0`, `0.03`, `50.0`, `80.0` 등)를 이름 있는 상수로 정의.
   - Phase 3에서 "순수 함수 테스트"가 성립하도록, `_sort_rows`(정렬 키/역순 여부를 인자로 받는 비교자 함수로)와 `_bar`(색상 활성화 여부 `enable_color`를 인자로 받는 함수로)를 인스턴스 상태에 의존하지 않는 free function으로 추출한다. `SystemMonitor`는 이 함수들을 호출하는 얇은 래퍼만 유지한다.

### Phase 3 — 테스트

6. 순수 함수(`_format_uptime`, `_format_time_plus`, `_to_mib`, `_sort_rows`, `_bar` 등 — 패키지 전환 후 새 모듈 경로 기준)에 대한 `pytest` 단위 테스트를 추가한다.

### Phase 4 — 기능 추가

7. 갱신 주기(`update_interval`) 키보드 조작 추가 (`+`/`-` 키, 0.5초 단위).
8. 전체 명령줄(cmdline) 표시 토글 추가 (`e` 키, `name` ↔ `cmdline` 전환). `cmdline`은 토글이 켜진 동안에만, PID당 1회 온디맨드로 `proc.cmdline()`을 호출해 `ProcCacheEntry`에 캐싱한다(이름 캐싱과 동일한 수명 주기 — 2초 이상 보이지 않으면 함께 정리). 토글이 꺼져 있으면 기존처럼 `name`만 사용해 추가 시스템 콜이 발생하지 않도록 한다(저오버헤드 샘플링 목표 유지).
9. 개별 CPU 코어 사용률 표시 추가 (`psutil.cpu_percent(percpu=True)`). 토글 키는 `1`(기본값 꺼짐 — `e`는 이미 cmdline 토글에 사용 중이므로 충돌 방지). 코어가 많은 환경에서는 한 줄에 4개씩 묶어 표시하고, 필요한 줄 수(`ceil(cpu_count / 4)`)만큼 `_build_screen`의 `max_proc_rows` 계산(`height - 11`)에서 동적으로 빼서 프로세스 테이블 공간을 확보한다.
10. `--no-color` / `--interval` CLI 인자 지원 (`argparse` 기반).

### Phase 5 — 폴리시

11. `pyproject.toml` 추가 (PEP 517/518, 프로젝트 메타데이터).
12. `--version` 플래그 및 `__version__` 상수 추가.

(참고: `q` 입력 즉시 종료 버그는 이미 수정 완료된 항목으로 TODO.md에 체크되어 있었다 — 이 로드맵에서는 다루지 않는다.)

## 9. builder에게 맡기는 부분

- 패키지/모듈의 정확한 이름, 파일 경계, import 구조.
- entry point 스크립트 이름 및 `pyproject.toml`의 `[project.scripts]` 구성(예: `top-python` 명령 제공 여부).
- dataclass vs `TypedDict` 중 최종 선택.
- 색상 상수를 `enum.Enum`으로 할지 단순 모듈 상수로 할지.
- EMA 로드 평균의 평활 계수(smoothing factor) 등 세부 수치.
- `--no-color`/`--interval`/`--version` 인자의 정확한 플래그 이름과 `argparse` 구성.
- 버전 번호 체계(예: `0.1.0`에서 시작).
- 각 Phase를 실제로 몇 개의 PR/커밋으로 나눌지.

## 10. 완료 기준

- 위 12개 항목이 모두 구현되고, `python system_monitor.py`(또는 새 엔트리포인트)가 기존과 동일하게 동작하며 회귀가 없다.
- `pytest`로 추가된 단위 테스트가 통과한다.
- README의 키 도움말과 실제 동작이 일치한다(특히 `interval` 조작 관련 기존 불일치 해소).
- `TODO.md`는 삭제되고, 이 문서가 백로그의 단일 출처가 된다.
